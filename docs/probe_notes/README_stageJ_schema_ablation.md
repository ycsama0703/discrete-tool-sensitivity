# Stage-J probe — 接口 vs 模型缺陷：四档 schema 消融

**Status: DONE（2026-09-25）。结果对"绑定缺陷"叙事不利，但暴露了更深的逻辑——见 §4。**

## 为什么做这个探针

所有错误率（25.9–38.2%，12 配置）都在一个 `period` **非必填**、描述极简的 schema 下测得。
审稿人必问：有多少是模型绑定失败，有多少只是 schema 设计太烂？

本探针固定模型（qwen2.5-7b）、问题、symbol、ladder，只变 schema：

| 变体 | 改动 | 目的 |
|---|---|---|
| S0 | baseline：`required: [symbol]` | 复现既有错误率 |
| S1 | `required: [symbol, period]` | 必填性是否有效 |
| S2 | S1 + 详细描述（**点名测试集字段**） | 描述质量是否有效 |
| S3 | S2 去掉指向测试集的提示 | 控制 S2 是否泄漏 |

**预注册判读**（跑前固定）：
- 若 S1/S2 把错误率压到 ~10% 以下 → 绑定缺陷大部分是接口缺陷，框架要改。
- 若扛过 → schema confound 被排除，现有数字站得住。

## 结果（各 400 case）

| 变体 | 改动 | 错误率 | 错误值 |
|---|---|---|---|
| S0 | 非必填 | **28.0%** | 全 `all` |
| S1 | 必填 | **27.3%** | 全 `all` |
| S2 | 必填 + 详细描述（含提示） | **0.0%** | — |
| S3 | 必填 + 通用描述（去提示） | **1.8%** | 全 `all` |

**三个事实：**
1. **`required` 无效**（S0→S1：28.0%→27.3%）。模型不是漏填，是填了 schema 合法的错误值 `all`。
2. **描述质量完全消除错误**（S1→S2：27.3%→0.0%）。
3. **S2 的 0% 不是泄漏**（S3 用通用描述也达 1.8%）。

## 表面结论（预注册判读触发）

S1/S2/S3 都压到 ~10% 以下 → **"绑定缺陷"大部分其实是接口缺陷**。详细描述就能消除错误，
筛查器似乎在防一个能轻易修掉的接口问题。

## 但 S2/S3 的正确地位是 bonus，不是主线判据

**S2/S3 不是"接口能修好，筛查器没必要"的证据，恰恰相反，它们加强主线。**

S2/S3 测的是：**"我已经明确告诉你哪里可能出问题了（quarter 和 fy 是不同的），你（模型）能不能
detect？如果错了能不能改？"** 这是一个**更强的测试**——它给了模型"作弊级"的帮助（直接告诉它歧义
在哪），看它能不能做对。

结果：S2/S3 压到 0–1.8% → **模型在"被告知歧义"的情况下，确实能 detect 并改对。**

**这为什么加强主线？** 主线是"模型不知道哪里会出错，所以需要筛查器"。S3 证明的是"模型在知道哪里
出错时能 detect"——这恰恰说明：
- 模型**有能力** detect（不是模型笨）；
- 但**它不知道要 detect 什么**（不知道歧义在哪）；
- 所以问题不在"模型能力"，而在"**模型不知道检查哪里**"；
- 而"知道检查哪里"只能靠枚举探测（=筛查器）。

**S3 把"模型能力问题"排除掉了，把问题精确锁定在"不知道检查哪里"上。** 这是对主线的**加固**，不是否定。

### 四档的完整意义

| 变体 | 测什么 | 结论 | 对主线的作用 |
|---|---|---|---|
| S0 | 泛化描述（认真检查） | 28% 错误 | **主线**：模型不知道检查哪里 → 需要筛查器 |
| S1 | 必填 | 27.3% | **主线**：required 无效，不是漏填 |
| S2 | 详细描述（点名字段） | 0% | **bonus**：告诉模型歧义，它能 detect |
| S3 | 通用描述（去泄漏） | 1.8% | **bonus**：即使不点名，只要强调歧义，模型也能 detect |

**S0/S1 是主线**（证明"不知道检查哪里"→ 需要筛查器），**S2/S3 是 bonus**（证明"知道歧义后模型能
detect"，排除"模型能力"这个替代解释）。

### 反事实：如果 S2/S3 压不下去会怎样

如果 S2/S3 也压不下去（模型被告知歧义还是错）→ 那才是"模型能力问题"，主线（筛查器）反而被削弱。
但 S2/S3 压下去了（模型被告知歧义就能 detect）→ **排除"模型能力"，锁定"不知道检查哪里"** → **主线
被加强**。

**S2/S3 压到 0–1.8% 是主线想要的理想结果，不是坏消息。** 它证明了：模型有能力 detect，缺的只是
"知道检查哪里"，而筛查器补的正是这个。

## 但这里有一个更深的逻辑（本文档的核心）

**S2/S3 的"修好"依赖一个隐藏前提：我们预先知道模型会在哪里出错。**

- S2 的描述有效，是因为我们**已经知道**测试集里的模糊字段（`current assets`、`shareholders' equity`）。
- S3 的通用描述有效，是因为我们**已经知道** `quarter` vs `fy` 是核心歧义，所以能写"quarter 和 fy
  是不同的东西，不是近似"。

**但强调"quarter 和 fy 是不同的"这个动作本身，就预设了你已经知道歧义在哪。** 一个不知道模型会在
`period` 上翻错的 schema 作者，不会想到要写这句话。

### 真实描述只能做到什么

真实世界的 schema 作者，在不知道哪里会出错的情况下，只能写出**泛化描述**：

> `period`: 报告期间。可选值：quarter（季度）、fy（财年）、all（全部）。请认真检查，确保选择正确。

它列了枚举值 + 提示"认真检查"，但**没有强调任何特定歧义**——因为作者不知道哪里有歧义。

### 为什么"认真检查"无效

**"认真检查"这个提示，只有在模型知道"哪里可能错"时才有用。** 而模型不知道——这正是问题所在。
模型填 `all` 的时候，不觉得自己错了：`all` 在 enum 里、schema 合法、语义上"两个都要"看似合理。
你告诉它"认真检查"，它检查了，还是觉得 `all` 对。

Stage-J 的 S0 就是这种泛化描述（"quarter = single quarter, fy = fiscal year, all = both"），
错误率 **28%**——证明"认真检查"无效。

### 真正的逻辑链

1. **真实描述**只能做到：列枚举值 + 提示认真检查（S0 那种）。
2. **"认真检查"无效**，因为模型不知道要检查什么（28% 错误）。
3. **要降低错误，必须告诉模型"哪里可能错"**（如"quarter 和 fy 是不同的"）。
4. **但"哪里可能错"你预先不知道**——只能靠枚举探测发现。
5. **枚举探测 = 筛查器**。

**筛查器的价值：它不需要"知道哪里可能错"，它枚举所有值重算决策。** 它不依赖"认真检查"（无效），
也不依赖"针对性提示"（需要先验知识）——它直接枚举，看决策是否翻转。

## 这如何把筛查器的价值找回来

筛查器（枚举离散邻域重算决策）的价值恰恰在于：**它不需要知道哪里会出问题。** 它枚举所有 period 值、
重算决策、看是否翻转——不管模型填什么、不管描述写没写对，它都能抓住决策翻转。

**"筛查器 vs 描述"的根本区别：**
- **描述**：需要**先验知识**（知道哪里会翻错）才能写好 → 在真实世界不可靠，因为你不知道。
- **筛查器**：不需要任何先验知识，枚举重算 → 在真实世界可靠，因为它不依赖"知道哪里会出问题"。

**审稿人可能的反驳**："那你可以先枚举测出哪些参数敏感（Phase-0），再针对性写描述啊。"
这个反驳**恰恰证明了筛查器的价值**：Phase-0 的"测敏感度"**就是筛查器**。你不可能在写描述之前，
不用某种"枚举/探测"就知道哪里敏感。所以：
- 要么**先枚举探测**（=筛查器），那筛查器已经在工作；
- 要么**不探测直接写**，那回到 28% 的错误率。

**"写好描述"这个建议，在逻辑上预设了"你已经知道哪里敏感"——而知道哪里敏感的唯一方法，就是枚举
探测，也就是筛查器。** 筛查器不是可选的，它是"写好描述"的前提。

## 论文核心主张（重新定位）

> **离散参数错误无法靠"写好描述"消除，因为写好描述需要知道哪里会出问题，而知道哪里会出问题只能靠
> 枚举探测——这正是筛查器在做的事。筛查器不是"接口缺陷的替代"，而是"接口缺陷的检测前提"。**
